# IPFE-IA — OMNeT++ / Veins / SUMO simulation project

OMNeT++ 6.0.1 project implementing the IPFE-IA heterogeneous identity
authentication protocol over the Veins 5.2 802.11p stack, with vehicle mobility
driven by SUMO through TraCI. This is the experimental code behind the
*"Simulation Evaluation in a Realistic Vehicular Environment"* section of the
paper.

See **`../README.md`** for dependencies, the build procedure, the scenario
generators, the experiment harnesses and the methodology notes.

## Layout

```
veins-ipfeia/
├── src/                    protocol modules (C++ / NED / MSG)
│   ├── VehicleApp.{h,cc}   OBU: key collection, authentication, ciphertext reporting
│   ├── RSUApp.{h,cc}       RSU: relay, aggregation of ciphertexts, backhaul
│   ├── ASApp.{h,cc}        AS: one-to-many / one-to-one authentication,
│   │                       aggregated / per-ciphertext decryption
│   ├── IPFEIAMsgs.msg      802.11p messages + wired backend messages
│   ├── apps.ned            module declarations (package ipfeia)
│   ├── IPFEIAScenario.ned  network: Scenario + rsu[] + as
│   └── IPFEIASupport.h     CryptoCosts: per-primitive delays from the jPBC bench
│                           (src/Makefile is generated by `./configure`)
├── scenarios/              generated by ../make_real_scenario.py (not versioned),
│   └── rsu_positions*.ini  except these hand-written RSU placements
├── omnetpp.ini             experiment matrix (see the table below)
├── omnetpp_r15.ini         RSU-density variants (15 / 35 RSUs)
├── omnetpp_r35.ini
├── omnetpp_alpha3.ini      urban path-loss exponent (alpha = 3, 20 dBm)
├── omnetpp_alpha3_33dbm.ini  same, at the 802.11p maximum of 33 dBm
├── config.xml             802.11p path-loss / PHY configuration
├── config_alpha3.xml      same, with alpha = 3
├── configure              generates src/Makefile (run inside an OMNeT++ shell)
├── Makefile               top-level build
├── run_sim.sh             one run: veins_launchd + opp_run -> results/
├── run_all.sh             the full experiment matrix
├── run_smoke.sh           short end-to-end smoke test
├── analyze.py             parse results/*.log -> results/summary.csv
└── results/               summary.csv + figs/ (per-run logs are not versioned)
```

## Build

```sh
# inside an OMNeT++ shell
./configure --with-veins=../veins-src
make MODE=release          # -> src/libipfeia.dll
```

## Run

```sh
./run_sim.sh O2M_AGG c100_v50      # -> results/c100_v50_O2M_AGG.log
./run_smoke.sh                     # quick end-to-end check
./run_all.sh                       # full matrix, ~300 s sim-time per run
```

## Configurations (`omnetpp.ini`)

| Config | AS authentication | AS decryption |
|---|---|---|
| `O2M_AGG` | one-to-many (broadcast delta, aggregate verify) | aggregated (constant cost) |
| `O2M_PAPER` | one-to-many | per-ciphertext, *d* × Dec |
| `O2O_AGG` | one-to-one (per vehicle) | aggregated |
| `O2O_PAPER` | one-to-one | per-ciphertext |
| `CMP_HE2023` / `CMP_HASSAN2022` / `CMP_SEIFELNASR2024` | representative one-to-one signature-based competitors | aggregated |
| `CMP_BLS_BATCH` | representative BLS batch/broadcast verification | aggregated |
| `GUI` | Qtenv with the campus map as canvas background (screenshot only) | — |

Competitor configurations are charged the primitive composition of their own
algorithm (`o2oDelta*`, `o2oVerify*`, `signEg1Count`, `authMsgBytes`) while
sharing the same measured jPBC unit costs, message lengths and 802.11p/WAVE
stack, so the difference between the curves comes only from the authentication
algorithm.

Key protocol parameters: `eta = 3` (key-extraction threshold), `n = 10` (vector
dimension), ciphertext reporting period 5 s, re-authentication period 30 s, RSU
aggregation window 5 s, AS batch / response window 0.5 s / 0.8 s, RSU–AS
backhaul 10 ms, discrete-log decryption range 2¹⁰.

## Log format (IPFEIA_LOG)

Each application prints CSV lines on stdout (grep `IPFEIA_LOG,`):

```
KEY_GOT,<veh>,<t>,<rsuIdx>,<keyCount>          VSK_READY,<veh>,<t>,<msSinceStart>
AUTH_REQ,<veh>,<t>,<round>                     REAUTH_START,<veh>,<t>,<round>,<kmh>
DELTA_VERIFIED,<veh>,<t>,<round>               AUTH_OK,<veh>,<t>,<latencyMs>,<round>,<initial|reauth>
AUTH_FAIL,<veh>,<t>,timeout,<retries>          JOIN_DONE,<veh>,<t>,<joinMs>
CT,<veh>,<t>,<encMs>                           CHAN,<entity>,<t>,<bytesSent>,<bytesRecv>
RSU_AGG,<rsu>,<t>,<d>,<n>,<aggMs>              RSU_SUMMARY,<rsu>,<aggs>,<sentB>,<recvB>
AS_DELTA,<t>,<round>,<d>,<ms>,<o2m|o2o>        AS_ACK,<t>,<round>,<resp>,<d>
AS_DEC,<t>,<d>,<n>,<ms>,<paper|aggregated>     AS_SUMMARY,...
VEH_SUMMARY,<veh>,<ok>,<fail>,<ct>,<bytes>,<everAuthed>
```

## Outputs

* `results/summary.csv` — one row per run, written by `analyze.py`.
* `results/figs/{scalability,latency,decryption}.png` — the paper figures,
  written by **`../analyze_ci.py`** (five-seed means ± 95 % CI). `analyze.py`
  deliberately does not draw anything, so a stale figure cannot shadow a fresh
  one.
